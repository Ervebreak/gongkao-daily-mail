# 公考晨读邮件项目工作流 Workflow

## 1. 文件定位

本文件用于定义“公考晨读邮件”项目从文章抓取到邮件发送、归档复盘的完整工作流。

它回答的不是：

- 产品是什么；
- 模块怎么写；
- 哪些内容不能出现；

而是：

- 整个系统按什么顺序运行；
- 每一步的输入和输出是什么；
- 哪些环节必须检查；
- 哪些结果需要沉淀；
- 测试模式和正式模式如何分开；
- 什么时候进入 PDF、归档和知识库。

本文件与以下文件配套使用：

- `product_spec.md`
- `content_rules.md`
- `framework_map_skill.md`
- `daily_question_skill.md`
- `takeaway_expression_skill.md`
- `quality_checks.md`

---

## 2. 工作流总目标

本项目工作流的目标是：

1. 稳定抓取适合公考/考编的官方文章；
2. 选出最适合作为“今日精读”的主线文章；
3. 生成一封适合手机阅读、可用于申论/面试积累的晨读邮件；
4. 在正式发送前尽量拦住明显不合格内容；
5. 将每日结果沉淀为归档、周 PDF 和知识资产；
6. 逐步形成“规则—生成—检查—归档—复盘”的闭环。

一句话理解：

> Workflow 负责把“内容生成”变成“可重复、可检查、可沉淀的生产流程”。

---

## 3. 总体流程总览

当前阶段的推荐工作流如下：

```text
抓取候选文章
→ 标题/来源/日期/URL/正文对应与完整性核验
→ 程序初筛
→ 第一阶段模型选文
→ 提取精读正文
→ 第二阶段模型生成邮件内容
→ 原文—候选事实一致性审稿与关键模块质量检查
→ 清洗和补救
→ 渲染 HTML
→ 测试模式 / 正式模式发送
→ 正式归档
→ 周指定日期生成 PDF
→ 记录问题与复盘
→ 沉淀知识资产
```

---

## 4. 工作流阶段划分

本项目当前工作流分为 9 个阶段：

1. 内容采集阶段
2. 内容筛选阶段
3. 内容生成阶段
4. 内容质检阶段
5. 渲染与发送阶段
6. 归档阶段
7. 周 PDF 阶段
8. 问题沉淀阶段
9. 知识复用阶段

下面分别说明。

---

## 5. 阶段 1：内容采集阶段

### 5.1 目标

从设定的官方或准官方来源中抓取候选文章，形成当天可供筛选的候选池。

### 5.2 输入

- 来源列表
- 栏目 URL
- 抓取日期范围
- 历史抓取记录（如有）

### 5.3 当前重点来源

当前优先来源包括：

- 人民日报
- 新华社
- 人民网评 / 人民锐评
- 半月谈
- 浙江宣传
- 光明网
- 人民论坛
- 其他具有公考转化价值的评论类文章

### 5.4 输出

候选文章列表，每篇至少包含：

- 标题
- 来源
- URL
- 发布时间
- 完整正文；摘要或正文片段不能替代
- 正文指纹、段落编号、抓取时间与完整性状态
- 栏目信息（如有）

### 5.5 注意事项

- 优先抓有公考转化价值的评论、分析、治理类文章；
- 纯会议报道、活动通稿、弱转化文章应降低权重；
- 抓取阶段不做最终写作判断，但必须核对标题、来源、日期、URL 与正文的对应关系。HTTP 200 和正文长度不能单独证明完整；正文不足时有限重抓，仍无法确认则记录未完成并排除主文，生产模式不得用样例文章兜底。

---

## 6. 阶段 2：内容筛选阶段

### 6.1 目标

从候选池中选出：

- 1 篇精读文章
- 1-2 篇速读文章

### 6.2 分两层完成

#### 第一层：程序初筛

程序按以下条件进行初筛：

- 日期范围
- 正文长度
- 历史去重
- URL 去重
- 标题相似度
- 来源优先级
- 栏目限制
- 基础主题相关性

目标是减少明显不适合进入模型池的文章。

#### 第二层：第一阶段模型选文

模型从程序初筛后的候选池中，选出：

- 最适合做“今日精读”的主线文章；
- 最适合做“今日速读”的补充文章。

选文 Prompt 采用“固定规则 + 动态上下文”：

- 固定规则来自 `content_harness/article_selection_prompt.md`，包括考题转化度、问题意识、场景具体度、矛盾张力、素材提炼价值、来源权威与时效。
- 动态上下文由程序注入，包括最近7天精读文章、最近3天主题/来源、昨日精读标题、今日候选池和来源统计。
- 当前已轻接入申论题库，但题库不参与选文阶段，因此选文评分项仍使用“考题转化度”，不得写成“真题相似度”。题库只在精读文章确定后，为“今日一题”提供隐藏问法参考。
- 评分只评价已核验原文，不得用后续模拟情节、题目、答案或润色结果抬分；有效总分统一保存在 `_llm_two_stage.selection.featured`，其他摘要字段由此派生。重评仅限新增原文证据，并保留旧版本与原因。

### 6.3 选文原则

精读文章优先满足：

1. 主题具体；
2. 有明显公考转化价值；
3. 结构较完整；
4. 能提炼框架图；
5. 能转化为今日一题；
6. 不与近几日主题重复；
7. 来源质量较高。

速读文章优先满足：

1. 与精读主题相关；
2. 可补充案例、表达或视角；
3. 不与精读内容重复；
4. 数量控制在 1-2 篇。

### 6.4 输出

- featured_article（精读文章）
- quick_read_articles（速读文章列表）

---

## 7. 阶段 3：内容生成阶段

### 7.1 目标

基于精读文章和速读文章，生成整封邮件的结构化内容。

### 7.2 生成方式

当前推荐采用两阶段模型：

#### 阶段 A：选文模型

输入候选池，输出精读文章和速读文章。

#### 阶段 B：写稿模型

输入：

- 精读文章完整正文
- 速读文章摘要/正文片段
- 文章结构
- 内容规则
- 模块 Skill
- 历史质量规则（后续逐步接入）

输出每日邮件各模块内容。

### 7.3 当前目标模块

当前阶段主要生成：

1. 顶部主题卡
2. 今日 3 件事
3. 今日精读
4. 文章框架图
5. 今日一题
6. 今日可带走
7. 今日速读
8. 反馈尾注（轻量）

### 7.4 文档层约束

在真正接入代码前，生成逻辑应遵守以下文档：

- `content_rules.md`
- `framework_map_skill.md`
- `daily_question_skill.md`
- `takeaway_expression_skill.md`

后续可逐步将这些文档注入 prompt 或转为更硬的脚本检查。

### 7.5 输出

一个结构化 daily_content 对象，至少包含：

- date
- theme
- featured_article
- article_framework_map
- daily_question
- takeaway
- quick_reads
- html_ready_fields

---

## 8. 阶段 4：内容质检阶段

### 8.1 目标

在正式发送前，尽量拦住明显不该发出去的内容。

### 8.2 当前优先质检模块

1. 文章框架图
2. 今日一题
3. 今日可带走 / 金句表达
4. 原文链接
5. 周 PDF（如当日触发）

### 8.3 检查依据

当前以以下文档为准：

- `content_rules.md`
- `quality_checks.md`

### 8.4 当前推荐检查器

后续代码层建议逐步对应为：

- `question_quality.py`
- `framework_quality.py`
- `content_cleaner.py`
- `pdf_quality.py`

### 8.5 当前高优先级检查项

#### 文章框架图

- 是否贴合原文结构
- 是否出现孤立数字
- 是否有半句话
- 是否节点数异常
- 是否误加“考场迁移”等非文章结构节点

#### 今日一题

- 是否过于宏观
- 是否与精读文章直接相关
- 是否有身份 / 场景 / 矛盾 / 任务
- 是否有考生版参考答案
- 是否答案被截断

#### 今日可带走

- 金句是否说明怎么用
- 表达是否考生化
- 是否与其他模块大量重复
- 关键词是否是考点词

#### 整体清洁度

- 是否出现待补充
- 是否出现 Python 列表格式
- 是否出现技术字段
- 是否出现重复字段名
- 是否出现明显异常文本

### 8.6 检查结果处理方式

检查结果可分为：

- P0：阻断发送
- P1：建议修复后发送
- P2：记录并后续优化

### 8.7 当前建议处理逻辑

- P0：必须修改或重写后再正式发送
- P1：优先修复，来不及时至少记录问题
- P2：允许发送，但必须进入问题日志

---

## 9. 阶段 5：渲染与发送阶段

### 9.1 目标

将结构化内容渲染为最终 HTML 邮件，并根据测试 / 正式模式发送。

### 9.2 渲染目标

HTML 应满足：

- 手机阅读友好
- 模块层级清晰
- 重点前置
- 不出现技术字段
- 原文链接尽量可用
- 周 PDF 附件或链接在指定日期生效

### 9.3 发送模式

#### 测试模式

事件示例：

```json
{
  "mode": "test"
}
```

测试模式应：

- 只发送给 `TEST_RECIPIENTS`
- 使用 `TEST_LLM_MODEL`
- 不写入正式 sent_history
- 不写入正式 daily 归档
- 不进入周 PDF 素材库

#### 正式模式

定时触发事件为空：

```json
{}
```

正式模式应：

- 使用 `LLM_MODEL`
- 读取 active 用户
- 正式发送
- 写入 sent_history
- 保存归档
- 在周指定日期附带周 PDF

### 9.4 输出

- 发送日志
- 成功 / 失败结果
- recipient_source
- success_count / fail_count

---

## 10. 阶段 6：归档阶段

### 10.1 目标

将正式发送内容沉淀为可复盘、可汇编、可复用的日级归档。

### 10.2 当前建议保存内容

正式发送后至少保存：

- `daily/YYYY-MM-DD.json`
- `daily/YYYY-MM-DD.html`

后续建议增加：

- `daily/YYYY-MM-DD.md`
- `knowledge/daily_outputs.jsonl`

### 10.3 归档用途

归档用于：

1. 生成周 PDF；
2. 后续月刊；
3. 内容质量复盘；
4. 优秀样例沉淀；
5. 知识库检索；
6. 用户反馈对照分析。

### 10.4 注意事项

- 测试模式不得污染正式归档；
- 非正式时间窗口内，如有特殊测试，也不得自动进入周 PDF 素材库；
- 归档内容应尽量保留结构化字段，而不是只保存最终 HTML。

---

## 11. 阶段 7：周 PDF 阶段

### 11.1 目标

在指定日期生成一周内容的 PDF 复盘资料，并作为邮件附件或链接发送。

### 11.2 当前定位

当前阶段的周 PDF 应优先满足：

- 一周每日晨读完整汇编；
- 适合打印和保存；
- 适合周末集中复盘；
- 不丢内容；
- 不重复每日反馈尾注；
- 不出现测试说明、空白页、乱码、技术字段。

### 11.3 当前工作流

当命中 `WEEKLY_PDF_WEEKDAY` 时：

```text
读取最近 N 天 daily 归档
→ 汇编成 PDF
→ 做 PDF 基础质检
→ 附件发送或生成链接
→ 保存到 weekly/ 目录
```

### 11.4 当前原则

在每日模块尚未稳定前：

- 按日期完整汇编
- 不强行按模块重组
- 不强行做真题区、素材区、框架区

### 11.5 输出

- `weekly/xxxx.pdf`
- 可选：PDF 下载链接
- PDF 发送日志

---

## 12. 阶段 8：问题沉淀阶段

### 12.1 目标

把已经出现过的问题从“聊天记忆”转移到“项目资产”。

### 12.2 当前主要沉淀位置

- `knowledge/quality_issues.jsonl`
- 运行日志
- 后续可加 `daily_outputs.jsonl`

### 12.3 记录内容

每条问题建议至少记录：

- 日期
- 模块
- 问题类型
- 具体坏例子
- 产生原因
- 修正规则
- 严重程度
- 是否已转为 Rule

### 12.4 当前已识别高频问题

- 框架图不贴原文
- 框架图出现孤立数字
- 框架图节点是半句话
- 今日一题过于宏观
- 今日一题答案不像考生
- 今日一题答案被截断
- 金句缺少用法
- PDF 强行重组导致内容缺失感
- PDF 重复反馈尾注
- PDF 基础可读性问题

---

## 13. 阶段 9：知识复用阶段

### 13.1 目标

让系统下次生成内容时，不再完全从零开始，而是逐步参考：

- 历史问题
- 历史优秀样例
- 真题库
- 表达素材库
- 每日输出库

### 13.2 当前阶段不做复杂数据库依赖

当前优先使用：

- `knowledge/quality_issues.jsonl`
- `knowledge/daily_outputs.jsonl`（后续）
- `knowledge/expression_bank.jsonl`（后续）
- `knowledge/exam_questions.csv`（后续）

先把知识结构跑通，再考虑数据库、向量检索或 RAG。

### 13.3 后续可演进方向

```text
读取历史质量问题 → 注入 prompt
读取同主题真题 → 辅助生成今日一题
读取优秀表达样例 → 辅助生成今日可带走
读取历史优秀框架图 → 辅助生成文章框架图
```

## 14. 测试模式与正式模式差异总表

| 项目 | 测试模式 | 正式模式 |
|---|---|---|
| 触发事件 | `{"mode":"test"}` | `{}` |
| 模型 | `TEST_LLM_MODEL` | `LLM_MODEL` |
| 收件人 | `TEST_RECIPIENTS` | active 用户 / subscribers |
| 是否写正式 sent_history | 否 | 是 |
| 是否写正式 daily 归档 | 否 | 是 |
| 是否进入周 PDF 素材库 | 否 | 是 |
| 是否允许只发自己 | 是 | 否 |
| 是否用于正式用户阅读 | 否 | 是 |

## 15. 当前阶段的最小闭环

当前阶段最小可行工作流闭环应满足：

```text
抓文章
→ 初筛
→ 选精读
→ 生成邮件
→ 检查今日一题和框架图
→ 渲染发送
→ 保存归档
→ 周 PDF 汇编
→ 记录问题
```

如果这个闭环稳定运行，再继续增加：

- 真题库
- 表达素材库
- 用户反馈按钮
- 打开率 / 点击率统计
- 知识检索注入
- 自动重写

---

## 16. 当前阶段不做的事

当前阶段暂不追求：

1. 复杂多 Agent 编排；
2. 全自动多轮重写；
3. 每天 PDF；
4. 复杂数据库和向量检索；
5. 全量用户行为统计；
6. 所有模块一次性自动重构；
7. 月刊 / 特刊自动化生产。

当前更重要的是：

- 流程清楚；
- 发送稳定；
- 规则沉淀；
- 质检有效；
- 归档完整；
- 问题可追踪。

---

## 17. 最终原则

Workflow 的价值，不在于把流程写得很复杂，而在于把以下事情变清楚：

1. 系统先做什么、后做什么；
2. 哪一步输入什么、输出什么；
3. 哪些内容必须检查；
4. 哪些问题不能进入正式发送；
5. 哪些结果必须沉淀下来；
6. 哪些测试不能污染正式系统。

一句话总结：

> Skill 定义“模块应该怎么写”，Workflow 定义“整套系统应该怎么跑”。

### 15.1 夜间审核与早晨发送的边界

夜间候选生成和 Publisher 负责完成正式内容审核，并把最终 `subject`、`brief`、`plain_text`、`html_body` 与 `quality_gate` 一起保存到候选件。

早晨 `morning_send` 只负责：

1. 读取指定日期的候选件；
2. 核对候选件日期和已保存的 `quality_gate.overall == ok`；
3. 检查发送所需成品字段存在；
4. 使用候选件中已保存的 Full 标题、纯文本和 HTML 发送；
5. 基于同一候选件渲染订阅分流所需的 Lite / 周报预览格式并发送。

早晨不得重新运行选文、事实、语义内容、清洁度或周报 PDF 质量检查，也不得从 `brief` 重新生成并覆盖已审核的 Full 成品。内容规则升级应作用于下一次候选生成或 Publisher 审核，不应把已经通过并上传的候选件在发送时再次打回。

---

## 16. 申论题库轻接入流程

题库接入位于“选文完成”和“最终邮件生成”之间。

### 16.1 运行顺序

```text
抓取文章
→ 选出精读文章和速读文章
→ 用精读文章匹配申论题库
→ 构造 question_bank_context
→ 注入最终生成 prompt
→ 生成邮件
→ schema 归一化
→ 模块质检
→ 必要时局部重写
→ 候选存档 / 发送
```

### 16.2 题库读取顺序

当 `QUESTION_BANK_SOURCE=oss`：

1. 从 `OSS_BUCKET + QUESTION_BANK_OSS_KEY` 读取 CSV；
2. 下载到临时路径；
3. CSV 读取成功后进入匹配；
4. OSS 失败时尝试本地兜底路径；
5. 本地也失败时返回空参考。

当 `QUESTION_BANK_SOURCE=local`：

1. 读取 `QUESTION_BANK_LOCAL_PATH`；
2. 路径相对程序根目录解析；
3. 失败时返回空参考。

### 16.3 失败处理

题库失败必须 fail-open：

```text
question_bank_refs = []
question_bank_warnings = [失败原因]
继续旧版今日一题生成
```

不得因为题库失败：

- 中断主程序；
- 阻断发送；
- 让 daily_question 为空；
- 改写订阅表、候选表或历史表；
- 触发额外发送。

### 16.4 日志和候选沉淀

每次生成应记录：

```json
{
  "question_bank_enabled": true,
  "question_bank_used": true,
  "question_bank_source": "oss",
  "question_bank_count": 296,
  "question_bank_refs": [],
  "question_bank_warnings": []
}
```

这些字段用于回答：

- 这次有没有启用题库；
- 读取的是 OSS 还是本地；
- 题库总数是多少；
- 命中了哪些参考题；
- 如果没用题库，是匹配不到还是读取失败。

### 16.5 与质检链路的关系

题库只影响生成 prompt，不直接决定门禁。

最终仍以以下检查为准：

- 今日一题是否具体；
- 是否与精读文章相关；
- 是否材料依赖；
- 作答框架是否过长或重复；
- 考生版答案是否自然完整；
- 质量门禁是否通过。
